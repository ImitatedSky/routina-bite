# Design: add-macro-widget

## Context

v0.8.0 的小工具（`BiteWidgetProvider`）是「動作型」：剩餘熱量、喝水進度、兩顆按鈕。
使用者看完的回饋是「只有喝水」「可以做更多小工具，例如今天所有飲食狀況」，
並補充要看的是**脂肪、蛋白質、碳水、熱量已經吃多少**。

這四個數字塞不進既有那塊——它已經壓在 2 格的 110dp 邊緣（見 `add-home-widget` 的 D56）。
所以是第二個小工具，不是改第一個。

## Goals / Non-Goals

**Goals:**
- 一眼看到今天吃進去的熱量與三大營養素
- 兩個小工具分工清楚：一個「狀態」、一個「動作」
- 填了三大營養素就不必自己算熱量，但要留得住手動指定

**Non-Goals:**
- 這個小工具不放按鈕（動作在另一塊）
- 不列出每一筆吃了什麼（要 collection widget，而且 4×2 放不下）

## Decisions

### D61. 第二個 provider，不是把第一個變大
兩個小工具各佔 2 格、各自回答一個問題，使用者要哪個就放哪個、兩個都放也行。
把六個數字擠進一塊的結果是兩個問題都回答得不清楚，而且會超過 110dp 被裁掉。

### D62. 三欄等寬，不照文字長度分配
`layout_weight="1"` 三等分。數字每天長度不同（`5.0` vs `168.2`），照內容分配的話
欄位會左右跳動，每天要重新找數字在哪。等寬之後位置固定。

### D63. 三大營養素色在深色主題要提亮一階
`MacroColors` 的三個值（#4E8A7B / #C2895A / #8A7BB5）是為了亮色底挑的低飽和色，
放在深色桌布上對比不足。`values-night` 另給一組提亮版本。
小工具長在別人的桌面上，亮暗不由我們決定——這條與 D60 同一個理由。

### D64. 熱量自動換算：蛋白質與碳水 4、脂肪 9
這是營養標示的通用換算，不是我們發明的係數。使用者填完三大營養素之後熱量就是已知的，
再要他自己乘一次是多餘的工。

### D65. 自動換算「可被覆寫」，而且回得去
- 使用者一動熱量欄 → `kcalIsManual = true`，之後改三大營養素不再覆蓋它
- **把熱量欄清空 → 交還自動換算**。這是唯一回到自動的方式，也是最直覺的：欄位空了就讓它自己算，
  不必為此多一個開關或一顆「重新計算」按鈕
- 從食物庫帶進來的熱量算「已經指定」（`basis.kcal > 0`）：**標示熱量本來就不等於 4/9/4 的換算**
  （`DayCompositionCard` 的註解講過同一件事），用換算蓋掉標示值等於竄改資料

### D66. 說明文字要寫出來
自動改動另一個欄位若沒有說明，使用者會以為是 bug。表單底下那行 hint 直接寫明
「填了三大營養素會自動算熱量，想自己填就直接改熱量欄（清空即回到自動）」。

## Risks / Trade-offs

- [使用者先填熱量再填三大營養素，熱量不會被更新] → 這正是「手動優先」的定義；
  想回到自動就清空熱量欄，hint 有寫。
- [換算值與食品標示的熱量有落差] → 所以只在使用者沒指定時才算；食物庫來的一律不動。
- [兩個小工具的 `requestCode` 撞在一起會讓 PendingIntent 互相覆蓋] → 第二個從 11 起跳。
