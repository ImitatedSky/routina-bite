# Design: auto-kcal-in-food-editor

## Context

`add-macro-widget`（v0.9.0）的 D64／D65 把「三大營養素換算熱量、但可手動覆寫」做進了
紀錄表單（`EntryFormState`）。食物編輯頁是另一份狀態（畫面層的 `remember`），沒有跟到。

## Decisions

### D71. 同一條規則，不同實作位置
食物編輯頁的欄位**就是「每一份」的值**，不像紀錄表單還要乘份數，所以換算是直接加總：
`4×蛋白質 + 9×脂肪 + 4×碳水`。三個觸發點（蛋白質／脂肪／碳水的 `onValueChange`）各加一行呼叫。

沒有把兩邊抽成共用的元件：一邊的來源是 `basis`（每份值）＋份數，另一邊直接就是每份值，
抽出來會多一層參數化，而重複的只有一個加法式子。

### D72. 「已經指定」的判定沿用 `kcal > 0`
編輯既有食物時，它的熱量是從營養標示抄來的，**標示值本來就不等於 4/9/4 的加總**，
所以一律視為已指定、不覆蓋。新建食物（熱量 0）才交給自動換算。

### D73. 清空熱量欄＝回到自動
與紀錄表單同一個回頭路，不另外加開關。

## Risks / Trade-offs

- [兩處各有一份換算邏輯] → 見 D71，抽共用的成本大於重複一個加法式子。
- [使用者抄標示時先填熱量再填三大營養素，熱量不會被改] → 那正是他要的順序。

## Open Questions

- 這一版的實機操作驗證沒做成：模擬器同時被另一個 Claude session 使用（它的 App 持續搶前景），
  無法穩定驅動 UI。已驗的是 `assembleRelease` 綠燈，以及同一條規則在紀錄表單上的實機結果
  （蛋白質 20 + 脂肪 10 → 170；手動 500 後改碳水仍為 500）。
