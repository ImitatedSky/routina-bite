# Design: decimal-calories

## Context

`formatKcal(value: Double): Int = value.roundToInt()` 從第一版就在，當時的想法是
「熱量取整數、其餘一位小數」（`add-bite-app` 的 D5）。那個決定對**合計**是對的，
對**單筆**是錯的：營養標示上就有兩位小數，而編輯頁是把標示抄進來的地方。

## Decisions

### D74. 兩個格式，依「單筆」或「合計」分
- `formatKcal`（整數）：一天的已吃／剩餘、餐別小計、歷史列、趨勢圖的軸與摘要、兩個小工具
- `formatKcalExact`（照實）：食物庫列、食物編輯頁、紀錄表單、今日頁每一筆、捷徑提示

分界不是「精不精確」而是**這個數字是誰產生的**：使用者抄進來的值要原樣還給他；
程式加起來的值四捨五入是合理的，一排 `1832.47` 比 `1832` 難讀，而那 0.47 不影響任何決定。

### D75. 整數不顯示小數點
`168` 不寫成 `168.00`。判斷用 `abs(value - roundToInt()) < 0.005`——
門檻取 0.005 是因為只留兩位小數，比這更小的差在顯示上本來就看不到。
與既有的 `formatAmount`（份數）同一套寫法。

### D76. 不動儲存
`Nutrients.kcal` 一直是 `Double`，備份檔裡也一直是小數。這次改的只是
「顯示」與「把值回填到輸入框」兩件事，沒有資料遷移。

## Risks / Trade-offs

- [同一畫面上單筆是 168.32、小計卻是整數] → 這是刻意的（D74），而且符合一般記帳與報表的慣例。
- [使用者輸入三位以上小數會被截成兩位] → 營養標示不會給到三位；真有需要再放寬。
