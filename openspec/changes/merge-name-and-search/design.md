# Design: merge-name-and-search

## Context

`inline-entry-form`（v0.6.0）把表單放進新增紀錄頁之後，畫面上就有兩個文字輸入：
最上面的「名稱」與食物庫上方的「搜尋食物（名稱或備註）」。使用者回報這是多餘的。

## Goals / Non-Goals

**Goals:** 一個輸入框，打字同時是「我要記的東西叫什麼」與「幫我在食物庫裡找它」
**Non-Goals:** 不動食物庫頁（那一頁沒有名稱欄，搜尋欄是它唯一的入口）

## Decisions

### D67. 名稱欄就是篩選條件
`val query = state.name`。不另外存一份搜尋字串——存兩份就會有「兩者不同步」這種
使用者永遠不會預期的狀態。

### D68. 有字時隱藏「常吃」「最近」
它們是「還沒想好要記什麼」時的捷徑。一旦開始打字，目標已經明確，
把不相干的十幾個食物留在畫面上只是擋路。名稱清空就回來。

### D69. 區塊標題寫出正在篩什麼
從固定的「搜尋結果」改成「符合「beef」的食物」。使用者在名稱欄打字時，
下面的清單會自己變短——不說明的話那看起來像 bug。標題直接寫出原因，成本是一個字串。

### D70. 選了食物之後清單只剩那一筆，這是對的
名稱被填成食物的名字，篩選條件跟著變。看起來像「清單塌了」，但它誠實反映了
目前的名稱，而且使用者這時的注意力已經在上面的表單。想再找別的就改名稱。

## Risks / Trade-offs

- [使用者打一個食物庫裡沒有的名字，清單會空掉並顯示「找不到符合的食物」] → 這正是他需要知道的：
  這東西不在庫裡，這一筆是一次性的。
- [名稱與搜尋合併後，無法「保留名稱但瀏覽整個食物庫」] → 要瀏覽有上方的「食物庫」入口。
